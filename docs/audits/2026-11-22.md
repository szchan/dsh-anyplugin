## Findings

### Baseline pass (00:20)

**F1/F2 — the push rule is tested but dormant; the digest (F2) reports it.** The push whitelist, write
confinement, worker merge denial and the merge-head pin are covered by tests, yet the install
status is `not-installed`, the pre-push hook is absent, and 23 stale worktrees
remain in its config. F1 is therefore `dormant`, not `enforced`; a mechanism
that is not installed prevents nothing.

**F13 — nearly every bash call repeats a `cd`.** 22,111 of 25,772 calls prefix
`cd <dir> &&`, while only 1,272 use `workdir`. The harness already carries the
directory, so the prefix is duplicated text in every call and in every result
that echoes the command.

**F14 — `verify` is used as a save button.** 950 full `verify` runs against 325
narrow `check:*` runs in the same window. Each run builds and runs 82 test files; the
narrow gate answers the same question for most edits.

**F15 — shell text tools outnumber the file tools.** `sed` 5,966 and `grep`
4,951 against `read` 1,148. The shell forms bypass the read tool's line
discipline, and frequently re-read a file that was already in context.

**F5 — the strongest review theme is a claim outrunning its test.** PR #89's
review thread (11 comments) records the exact shape: a callable was accepted,
but "the test proved the callable, not the promised contract". The S19 verdict
was "too strong". This is not one PR's mistake; it is the default failure when a
test is written after the claim.

**F4 — decision numbers collide under parallel work.** D51/D52/D53 and
D59/D60 were picked twice by concurrent workers. The append-only hash accepted
both entries because each was new and well formed; the collision was caught in
review, not by a gate.

**F12 — the merge head is not pinned.** Review verdicts are issue comments,
not GitHub reviews, and the guard only denied `gh pr merge` to workers. A
master can merge after new commits land, so "what was reviewed" and "what was
merged" can differ. #163 adds the every-role rule: a modelled `gh pr merge`
that performs a merge must carry `--match-head-commit <40-hex>`, including
`--auto`, with `-R`/`--repo`
between `pr` and `merge` or a value flag that could swallow the pin; any-method
`gh api .../merge` is refused. `--disable-auto` is allowed because it performs
no merge. The guard is `not-installed` here (F1), so F12 is
`dormant`; the installed mount denies an unpinned merge and allows a pinned one,
and the policy text in `docs/WORKFLOW.md` and this ledger is part of the fix. A
merge through an unmodelled client remains a residual, including a pre-existing
git/client-side alias that root may run. The pin prevents
omission, not review verification.

**F16 — denials are not observable.** A denial exists only as `DENY <rule> —
anyplugin-guard: …` inside a tool result. It is indistinguishable from the
guard's self-test output and from a file read, so the audit cannot say which
rules fire in real work. Tracked in #164; **closed 2026-11-22 by D68** (structured log, #181), so the ledger now reads `enforced`.
*(Corrected by the 09:00 pass: the merged log does not make the mechanism
active. The ledger now reads `dormant`; see the daily findings below.)*

**F17 — the audit would grade its own homework.** The same agent writes the
mechanism, the ledger, and the verdict unless the pass is reviewed
independently. This pass used two reviewers; the tool rejected
`agent_preset: "readonly"` ("selection is disabled for this tool instance"), so
they were plain subagents under a read-only brief. That is a weaker claim than
the sandboxed form, and is recorded as such.

**F18 — a root session runs past the role cap.** The largest root session ran
2,470 tool calls, above the ~1,500 cap, and the baseline pass did not notice.
The cap existed only as prose; the skill now requires the eight-largest check
and a named split for every root over the cap.
